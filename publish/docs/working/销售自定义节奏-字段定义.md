## 1. 业务问题

**现状**：

- `跟进策略 Skill` 页只提供 4 个预置节奏 chip（标准跟进 / 新能源专享 / 高意向加速 / 冷淡重激活），销售不能新增。
- 每个节奏的 SOP 是 4 步预定义（首次接洽 / 用户孵化 / 预审收集 / 转人工）。
- 收件箱 profile 区"AI 任务进度"硬编码渲染这 4 步（`{state, name, time}` 3 字段）。

**问题**：销售对不同车型 / 不同客户群体有差异化跟进经验，但无法沉淀成自己的节奏 → 经验不能复用、好的 SOP 只能平台预设。

**目标**（PM 决策 D11 提案 · 待确认）：

- 销售可创建 / 编辑自己的跟进节奏
- 收件箱任务进度根据所选节奏**自适应渲染**（步数不定、节点类型多样化）
- 转人工不再固定为"STEP 4"，而是销售可在任意位置插入的**普通 step**（决策项 #4）

|------|------|------|--------|------|------|

| `order` | int | ✅ | 系统 | 步骤序号 | 1, 2, 3... |
| `name` | string | ✅ | **销售** | step 标题 | "首次接洽" |
| `type` | enum | ✅ | 系统 | 节点类型（决定 UI 渲染） | `intro` / `nurture` / `precheck` / `wait` / `handoff` |
| `desc` | string | ⭕ | **销售** | 销售看的描述 | "客户刚接入，AI 完成首轮问候" |
| `duration` | string | ⭕ | **销售** | 期望时长 | "立即" / "24h" / "最长 3 天" |
| `trigger_on` | string | ✅ | **销售** | 进入条件 | "新线索接入" / "STEP 1 已读 + 简短回复" |
| `transitions` | Transition[] | ✅ | **销售** | **命名出口规则**：条件与去向必须在同一对象内绑定 | 见 §3.2.1 |
| ~~`exit_on`~~ | ~~string[]~~ | — | — | **已废弃（v1.2）**：不得再与 `exit_to` 平行数组配对 | 改为 `transitions[].condition` |
| ~~`exit_to`~~ | ~~string[]~~ | — | — | **已废弃（v1.2）**：不得表达一对多分支 | 改为 `transitions[].target_step_id` / `target_status` |
| `ai_system` | string | ⭕ | 系统 | AI 系统提示词（**销售改需走审核流**） | "你是 Maria，..." |
| `context_vars` | string[] | ⭕ | 系统 | AI 可读变量 | `["customer.name", "car.series"]` |
| `forbidden` | { word, action }[] | ⭕ | 系统 | 敏感词 + 处理动作 | `[{word:"利率", action:"立即转人工"}]` |
| `hsm_template` | string | ⭕ | 系统 | 关联 HSM 模板 ID | `hsm_welcome_v1` |
| `skippable` | bool | ⭕ | **销售** | 是否可被跳过 | false |
| `optional` | bool | ⭕ | **销售** | 是否可选步骤 | false |
| `parallel` | bool | ⭕ | **销售** | 是否与下一步并行执行 | false（MVP2 不支持） |
| `node_prompt_template` | object | ✅ | **销售** | 节点提示词结构化模板（不是自由文本） | 见 §3.6 |
| `output_schema` | object[] | ⭕ | **销售** | AI 必须返回的结构化字段 | `[{key:"budget", type:"number"}, {key:"intent", type:"enum"}]` |
| `trigger_type` | enum | ✅ | **销售** | trigger_on / exit_on 的条件类型 | `keyword` / `regex` / `field` / `time` |
| `dry_run_required` | bool | ✅ | 系统 | 是否必须测试沙盒通过才能保存 | true（修改时强制） |

### 3.2.1 命名出口规则（`transitions[]` · v1.2）

> **核心问题**：旧模型用 `exit_on[]` + `exit_to[]` 两个平行数组，无法保证“条件 ↔ 去向”一一绑定。
>
> **反例**：`exit_on = "核心需求足够判断下一步，或客户明确不匹配"` + `exit_to = sop_03`
> - 命题 A「需求足够」→ 进入车型与金融方案引导，正确
> - 命题 B「客户明确不匹配」→ 仍进入车型与金融方案引导，**错误**；应关闭或转培育
>
> **原则**：每个业务结果是一条独立出口对象；条件、结果类型、目标节点/终态写在同一条规则里。MVP 用多出口表达分支，**不新增** `branch` 节点类型。

`transitions: Transition[]` 字段定义：

| 字段 | 类型 | 必填 | 说明 | 示例 |
|------|------|------|------|------|
| `id` | string | ✅ | 出口唯一 ID | `sop_02_t2` |
| `label` | string | ✅ | 出口名称（给人看） | `明确不匹配` |
| `condition_type` | enum | ✅ | 条件类型 | `keyword` / `regex` / `field` / `time` / `fallback` |
| `condition` | string | ✅ | 本出口成立条件；`fallback` 固定为「其他未识别情况」 | `vehicle.new_car_need = false` |
| `outcome` | enum | ✅ | 结果类型 | `continue` / `stay` / `wait` / `nurture` / `close` / `handoff` / `manual` / `complete` |
| `target_step_id` | string \| null | ⭕ | 跳到的下一步 ID；终态出口为 null | `sop_03` |
| `target_status` | enum \| null | ⭕ | 终态；跳节点时为 null | `nurture` / `wait_until` / `closed` / `manual_hold` / `formal_progress` / `purchased` / `completed` |
| `priority` | int | ✅ | 匹配优先级，**数字越小越先匹配** | `10` |
| `is_default` | bool | ✅ | 是否默认兜底；每节点恰好 1 条且 `condition_type=fallback` | `true` |

匹配与校验规则：

1. 按 `priority` 升序匹配，命中第一条即停。
2. 每个 step **至少 1 条** `transitions`，且 **恰好 1 条** `is_default=true` 的 `fallback`。
3. `continue` 必须有 `target_step_id`；`stay` 可指向当前节点或仅设 `outcome=stay`；终态出口必须有 `target_status`。
4. 禁止把互斥结果用 `OR` 塞进同一条规则再共用一个去向。
5. 保存时做死路校验：有向边不得形成无兜底死循环；被引用的 `target_step_id` 必须存在。

示例（`sop_02` 需求确认）：

```js
transitions: [
  {
    id: 'sop_02_t1',
    label: '需求明确且仍在考虑',
    condition_type: 'field',
    condition: 'vehicle.new_car_need = true AND (vehicle.model OR vehicle.direction) 已明确',
    outcome: 'continue',
    target_step_id: 'sop_03',
    target_status: null,
    priority: 10,
    is_default: false
  },
  {
    id: 'sop_02_t2',
    label: '明确不匹配',
    condition_type: 'field',
    condition: 'vehicle.new_car_need = false OR 服务范围不匹配',
    outcome: 'close',
    target_step_id: null,
    target_status: 'closed',
    priority: 20,
    is_default: false
  },
  {
    id: 'sop_02_t3',
    label: '暂时没准备好但未来可能购车',
    condition_type: 'field',
    condition: 'purchase.timing = later OR 客户要求稍后联系',
    outcome: 'nurture',
    target_step_id: null,
    target_status: 'nurture',
    priority: 30,
    is_default: false
  },
  {
    id: 'sop_02_t4',
    label: '其他情况转人工判断',
    condition_type: 'fallback',
    condition: '其他未识别情况',
    outcome: 'manual',
    target_step_id: null,
    target_status: 'manual_hold',
    priority: 999,
    is_default: true
  }
]
```

### 3.3 节点类型（`type`）枚举

| type | 含义 | 进度展示 | 是否计入主路径 |
|------|------|----------|---------------|
| `intro` | 首次接洽 | 单点 ✓ | ✅ |
| `nurture` | 孵化（多轮等待） | 节点 + "本轮：3/3 已完成" | ✅ |
| `precheck` | 预审收集 | 节点 + 字段进度 `3/8` | ✅ |
| `wait` | 等待客户回复 | 节点 + 倒计时 `剩 18h` | ✅ |
| `branch` | 分支判断 | 节点 + 2 个出口箭头（MVP2 不支持 UI） | ✅ |
| `handoff` | 转人工 | 特殊紫色标记（**现在作为 normal_step**） | ✅ |
| `manual` | 销售手动节点 | 节点 + "等销售操作" | ✅ |

**关键决策**：根据决策项 #4，**`handoff` 不再是"特殊出口"**，而是与其他 step 同级的普通 step。是否触发转人工由 `transitions[]` 条件决定。

### 3.4 任务进度运行时状态

进度状态由后端推，不是销售定义。展示形式受 `step.type` 影响。

| 状态字段 | 值 | UI 表现 | 备注 |
|---------|-----|---------|------|
| `state` | `done` / `active` / `pending` / `skipped` / `failed` | 颜色 + 图标 | `skipped` 新增；`failed` 新增 |
| `current_step_id` | step.id | 当前节点高亮 | 用于 stepper |
| `completed_step_ids` | step.id[] | 已完成列表 | 用于渲染 ✓ |
| `blocked_reason` | string? | 阻塞原因 | "等客户回复 22h" / "敏感词命中" |
| `eta_next` | ISO timestamp | 下次 AI 行动时间 | 下次 HSM 触发时间 |
| `last_action` | { at, type, summary } | 最近一次 AI 动作 | "10:23 HSM 发送 · 已读" |
| `progress` | object | 类型相关进度 | `precheck` → `{ collected: 3, total: 8 }`<br>`nurture` → `{ rounds: 1, total: 3 }` |

### 3.6 节点提示词结构化模板（v1.1 新增 · PRD 决策项 #1）

> **核心原则**：销售填的是"配置单"（表单字段），不是"提示词文章"。
>
> **依据**：LLM 对**结构化指令**的遵循率（80%+）远高于自由文本（30-50%）。
> 如果销售自由写，AI 会"看心情执行"，每次回复结果不一致。

`node_prompt_template` 是一个**结构化对象**，包含以下字段：

| 字段 | 类型 | 必填 | 说明 | 示例 |
|------|------|------|------|------|
| `role` | enum | ✅ | 销售人设（从下拉选） | `Maria / 销售顾问` |
| `persona_extra` | string | ⭕ | 销售附加人设（最多 200 字） | "专注新能源 · 西语口音亲切" |
| `current_stage` | string (auto) | ⭕ | 系统自动填充（STEP 名称） | "STEP 3 · 预审收集" |
| `objective` | string | ✅ | 本步要达成的目标（1-2 句） | "确认客户购车预算区间" |
| `available_vars` | string[] | ✅ | AI 可读取的变量（多选） | `[customer.name, car.series, customer.budget]` |
| `available_hsm` | string[] | ✅ | 本步可发送的 HSM 模板（多选） | `[hsm_welcome_v1]` |
| `forbidden_promises` | string[] | ⭕ | 禁止承诺（多选 + 自填，走审核） | `[利率, 零首付, 100%通过]` |
| `forbidden_action` | enum | ⭕ | 命中敏感词怎么办 | `transfer_human` / `rephrase` / `mark_silent` |
| `output_fields` | object[] | ⭕ | AI 必须返回的结构化字段 | `[{key:"budget", type:"number", required:true}]` |
| `few_shot` | {input, output}[] | ⭕ | 客户回复 → AI 回应的示例（最多 5 条） | `[{input:"太贵了", output:"Entiendo, ¿qué presupuesto manejas?"}]` |
| `tone` | enum | ⭕ | 语气 | `professional` / `friendly` / `enthusiastic` |

**运行时 prompt 拼装规则**（AI 引擎内部）：

```
[SYSTEM]
你是 {{role}}，{{persona_extra}}。
当前阶段：{{current_stage}}
本步目标：{{objective}}
可用变量：{{available_vars 拼接}}
本步可用 HSM：{{available_hsm 拼接}}
禁止承诺：{{forbidden_promises 拼接}}
命中敏感词 → {{forbidden_action}}
Few-shot 示例：
{{few_shot 列表}}

[USER]
客户最新消息：{{customer.last_message}}
客户上下文：{{available_vars 的实际值}}
历史对话摘要：{{conversation_history_summary}}

[ASSISTANT OUTPUT SCHEMA]
{{output_fields 的 JSON Schema}}
```

**销售填 vs 系统填 vs 系统托管 · 边界**：

| 子字段 | 销售可填 | 系统填 | 备注 |
|--------|:--------:|:------:|------|
| `role` | ✅（下拉）| | 人设枚举（Maria / Carlos / 自定义） |
| `persona_extra` | ✅（短文本 ≤200 字）| | |
| `current_stage` | | ⛔ | 系统自动 = step.name |
| `objective` | ✅（短文本 ≤100 字）| | |

## 4. 任务进度展示方案（决策项 #2 = A）

### 4.1 方案选型理由

- **A · 节奏自适应 stepper**：竖向 stepper，动态绑 `rhythm.steps[]`，最少 1 步最多 10 步
- 销售最常用 = 看到当前走到哪一步 + 下一步是啥，stepper 视觉密度刚好
- 超过 6 步节奏会变长滚动条，但销售可以折叠"已完成步骤"

### 4.2 渲染规则

```js
// 伪代码
function renderTaskStepper(rhythm, progress) {
  const visibleSteps = rhythm.steps.filter(step => {
    // 折叠已完成 step（默认保留最近 1 个已完成）
    if (step.id === progress.completed_step_ids.at(-1)) return true;
    if (progress.completed_step_ids.includes(step.id)) {
      return rhythm.steps.length <= 5; // ≤5 步全显示，>5 步折叠
    }
    return true; // pending / active / failed / skipped 全显示
  });

  return visibleSteps.map(step => `
    <div class="task-step ${progress.state_of(step.id)}">
      <div class="task-step-dot"></div>
      <div class="task-step-body">
        <div class="task-step-name">${step.name}</div>
        <div class="task-step-time">${formatStepTime(step, progress)}</div>
        ${step.type === 'precheck' && step.id === progress.current_step_id
          ? `<div class="task-step-progress">${progress.precheck.collected}/${progress.precheck.total} 字段已收集</div>`
          : ''}
      </div>
    </div>
  `).join('');
}
```

### 4.3 节点类型 → 展示细节

| type | step name 下方附加 |
|------|---------------------|
| `intro` | "立即触发 · 等待用户响应 4h" |
| `nurture` | "本轮：3/3 已完成 · 下次 24h 后" |
| `precheck` | "3/8 字段已收集"（实时进度条） |
| `wait` | "剩 18h · 自动沉默转入失活" |
| `branch` | MVP2 不支持，UI 仍按单线渲染 |
| `handoff` | 紫色块 + "转人工 · 任意时刻可触发" |
| `manual` | "待销售手动操作 · 等回复" |

### 4.4 转人工（handoff step）的展示变化

**现状**：固定在 stepper 最底部，独立紫色块，标"特殊出口 · 非主路径步骤"。

**改造后**：作为普通 step 进入主路径，不再有"特殊出口"标签；trigger 时机由 `transitions[]` 决定（如"客户表达预算 / 偏好 → 进入 handoff"）。

### 4.5 折叠 / 展开交互

- 默认折叠：步骤数 > 5 时，已完成 step（除最近 1 个）折叠为 "已完成 3 步 [+展开]"
- 异常 step（failed）始终展开并高亮红色
- 折叠时不破坏 stepper 视觉顺序

## 5. 落地路径（MVP2）

### 5.1 阶段拆分

| 阶段 | 工作量 | 交付物 |
|------|--------|--------|
| **MVP1**（当前） | — | 4 步预置 + 硬编码 stepper，无节奏编辑 |
| **MVP2.1** | 3 天 | Skill 页加 "新建节奏" drawer，输出字段按 §3.1-3.2 落地 |
| **MVP2.2** | 2 天 | 收件箱 profile 的 stepper 改成动态渲染（§4.1-4.5） |
| **MVP2.3** | 2 天 | `applies_to` 匹配逻辑 + 多节奏优先级 |
| **MVP2.4** | 3 天 | 节奏运行时调试（暂停 / 跳过 / 加速） |

### 5.2 MVP2.1 验收标准

- 销售能在 Skill 页"新建节奏"，输入节奏名 + 拖拽步骤顺序
- 每个 step 可编辑：name / desc / duration / trigger_on / transitions / skippable / optional
- 不可编辑字段：id / type / order / hsm_template（灰显 / 锁定）
- 保存节奏后立即生效（toast 提示"已下发运行中的 AI 跟进任务"——与现状文案对齐）
- 1 个客户 demo：自定义 5 步节奏"首联 → 等4h → 追问预算 → 试驾邀约 → 转人工"；其中“追问预算”至少配置 2 条命名出口（继续 / 拒绝关闭）

### 5.2.1 MVP2.1 表单校验规则（v1.1 补充 · PRD 决策项 #2）

| 校验项 | 规则 | 错误提示 |
|--------|------|----------|
| 节奏名 | 必填，1-30 字 | "请填写节奏名" |
| 步数 | 1 ≤ steps ≤ 10 | "节奏步数应在 1-10 之间（>8 步建议拆节奏）" |
| handoff step | **至少 1 个 step 的 type=handoff** | "节奏必须包含至少一个转人工步骤"（**PRD 决策项 #3 · block_save**）|
| trigger_type | trigger_on / transitions[].condition 必须指定类型 | "请选择条件类型（关键词 / 正则 / 字段 / 时长 / 兜底）" |
| transitions 绑定 | 每条出口必须同时有 label + condition + outcome + 目标（节点或终态） | "出口条件与去向必须写在同一条规则内，禁止平行数组" |
| 互斥结果禁止 OR 共用去向 | 不得把“匹配成功 / 明确不匹配”写进同一出口 | "请拆成两条出口规则" |
| 默认兜底出口 | 每个 step 恰好 1 条 `is_default=true` 且 `condition_type=fallback` | "请配置且仅配置一条默认兜底出口" |
| 目标有效性 | `target_step_id` 必须存在，或 `target_status` 属于终态枚举 | "出口目标未配置或不存在" |
| 自由文本提示词 | **禁止** `node_prompt_template.ai_system` 是 textarea 自由撰写 | 表单必须用结构化字段（§3.6） |
| forbidden 词库 | 修改走审核流 | "敏感词库修改已提交审核，预计 2 小时内反馈" |
| dry_run_required | 修改 prompt / forbidden 后必须测试沙盒通过 | "请先在测试沙盒跑通 1 个历史客户再保存" |
| 多节奏冲突 | 同 `applies_to` 范围下，priority 必须唯一 | "同车型已有节奏 X（priority=Y），请调整优先级" |

### 5.3 MVP2.2 验收标准

- 收件箱 profile "AI 任务进度"区，根据客户所用节奏的 `steps[]` 动态渲染
- 步数变化（3 步 / 5 步 / 8 步）布局自适应
- 节点类型 `precheck` 显示字段进度 `3/8`
- 节点类型 `handoff` 不再标"特殊出口"
- 超过 5 步自动折叠"已完成步骤"

### 5.4 数据兼容

- MVP1 的 4 步预置节奏迁移到 `rhythm.standard_v1`，保持现有客户体验不变
- 新节奏 `personal.*` 与 `team.*` 命名空间隔离
- 现有收件箱 mock 数据需调整：每个 profile 加上 `rhythm_id` 字段

## 6. 风险与开放问题

### 6.1 风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 销售乱建节奏 → SOP 失控 | AI 对话质量下降 | `ai_system` / `forbidden` 走审核流；`active` 字段需主管确认 |
| 节奏过多 → 客户被分配到错误节奏 | 跟进错配 | `priority` + `applies_to` 双重匹配；`is_default` 兜底 |
| 步骤过多 → stepper 视觉冗长 | 信息密度过高 | >5 步折叠已完成；>8 步弹警告"建议拆节奏" |
| 转人工身份变化 → 失去 SLA 监控 | 工时 SLA 失效 | handoff step 仍触发 `D6` 已定的 SLA 规则 |
| **销售自由写提示词 → AI 执行率低** | 客户回复不一致 | **结构化表单强制（PRD 决策项 #1）** |
| **trigger_on / transitions 写得模糊 → AI 走偏** | 节奏卡死 / 跳错 | **condition_type 枚举强制（keyword/regex/field/time/fallback）** |
| **互斥结果共用一个去向 → 错误推进** | 不匹配客户进入方案引导 | **transitions 对象绑定 + 保存校验禁止 OR 共用去向** |
| **forbidden 词库配错 → 误转人工 / 漏报** | 销售被淹没 / 违规 | **表单多选 + 自填走审核** |
| **节奏漏配 handoff → 转人工失效** | 客户无人接管 | **保存强制 ≥1 个 handoff step（PRD 决策项 #3 · block_save）** |
